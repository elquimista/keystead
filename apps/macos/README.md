# Keystead for macOS

A SwiftUI app on top of the shared Rust core, which is linked in as a static library
through Swift bindings generated by [UniFFI](https://mozilla.github.io/uniffi-rs/).

**Status:** the team owner can set up a team, invite and approve people, create and share
folders, and add logins; everyone can search, copy and change passwords, and bring their
account back on a new Mac with a Recovery Kit.

- **Main window:** on first launch, a welcome screen to join a team with an invite, set
  up a new one with the server's setup code, or recover an account with a Recovery Kit. Then folders and people on the left, logins
  and their details on the right. Double-click a login (or press Return or ⌘C) to copy its
  password. Each login can be edited (name, username, website, password and notes; notes
  stay hidden until shown, like the password), shared with a person or a group, or
  deleted for everyone who can open it. A login's website is a link only if it's a web
  address (http or https); anything else shows as text. The sidebar's rows stay put even when empty, and
  ⌘1 to ⌘7 go to them in order, from All Logins to Groups. Every list can be searched.
- **Login menu:** what can be done with the selected login, greyed out when its role
  doesn't allow it: Copy Username (⇧⌘C), Copy One-Time Code (⌥⌘C), Edit… (⌘E), Share… or
  Access…, History… (⌘Y), Move To… and Delete… (also the Delete key; it asks first).
- **Syncing:** on its own every 5 minutes while unlocked, and when you come back to the app
  after a minute or more; Vault › Sync (⌘R) syncs now. A sync asked for while one runs
  waits for it and then runs once, and a spinner stands in for the sync button meanwhile.
  If the server sends older copies of logins, folders or groups than this Mac has already
  seen, as one restored from a backup does, the Mac keeps its own and says so.
- **Moving logins:** Move To… (in a login's "⋯" toolbar menu or right-click menu) moves it to
  another folder you can add to, or out of folders as yours. Whoever had it only through
  the old folder loses it, and its password goes on their To Change list; people and
  groups it's shared with directly keep it. Needs a 0.12.0 server.
- **Renaming and deleting folders:** a folder's managers rename it or delete it from its
  right-click menu. Renaming renames the folders inside it they manage too, and everyone
  sees the new name; any server works. Deleting asks first, saying how many logins go
  with it, for everyone and for good, and which folders inside it stay. Deleting needs
  a 0.13.0 server.
- **Folders inside folders:** folders named like "Production / Databases" show nested in
  the sidebar. New Folder Inside… (a folder's right-click menu) makes one that starts out
  shared like its parent, or private. After that each folder has its own access: sharing
  one never shares another, and the Access sheet says so.
- **Invites:** an invite works once, for seven days. Until someone has used theirs, the
  owner sees them under People as invited, and can revoke the invite there: its line
  stops working at once. Needs a 0.16.0 server; an older one's invites work until used
  and aren't listed.
- **Roles and access:** folders and logins are shared to view, edit or manage. A folder's
  Access… (in its right-click menu or toolbar) lists its members; managers change roles
  and remove people, and anyone can leave. Actions someone's role doesn't allow are
  greyed out. The owner removes someone from the team under People. In a folder, roles
  are signed by its managers (0.17.0 server): the app goes by that, not by what the
  server says, so a change by someone who only views a folder is ignored, and the
  sync says so.
- **Groups** (Team › Groups, ⌘7): the owner makes groups; folders and logins are shared
  with a group as with a person, and reach everyone in it, including people added later.
  A group's managers in it add people; the owner and its managers remove people, rename
  it and change its managers. Taking someone out gives the group, and the folders shared
  with it, new keys in the background. Needs a 0.4.0 server. Delete Group… (0.10.0 server)
  takes away what only the group gave its members, and gives its folders new keys; it
  can't while the group is a folder's only manager.
- **To Change:** when someone loses access, the passwords they could see that you can
  change are listed under To Change in the sidebar, with a warning on each login and on the
  person's page. Saving a new password takes a login off; Keep It (or Keep All, for someone
  who only moved teams) keeps the password as it is. Needs a 0.5.0 server.
- **Password Health:** in the sidebar, the logins you can change whose password is weak,
  used for other logins too, or unchanged for over a year (old ones need a 0.13.0
  server). It's worked out on your Mac when you open it, and nothing about the passwords
  is kept.
- **One-time codes:** a login can keep the setup of a site's one-time codes (Edit, then
  paste the setup key or otpauth:// link, or the QR code button to read it from a screenshot).
  Its details then show the current code with the seconds it has left; copying it works
  like copying the password. Logins with codes need a 0.6.0 server, and apps before 0.6.0
  can't open them.
- **History:** History… (in a login's "⋯" toolbar menu) lists its earlier versions (the server keeps the last
  10): who saved each, when, and what it changed. Each one's password can be shown or
  copied, and Bring Back… saves it as a new version. Editors and managers only; needs a
  0.7.0 server.
- **Importing:** File › Import from Passbolt or KeePass… reads a Passbolt export (KDBX,
  with its passphrase), or a KeePass or KeePassXC file, shows which folders the logins go
  into (new ones are yours alone until shared), what's already here and left out, and
  imports only once you confirm. One-time codes come along; extra fields go into notes.
  Nothing decrypted is written to disk.
- **Recovering with the owner's help:** someone who lost every device and their Recovery
  Kit gets back in with new keys. The owner chooses Help Recover… on their page and sends
  the line it shows; on a new Mac they choose "Recover your account", then "Recover with
  your team owner's help", paste it, and read the new fingerprint to the owner, who
  approves it. Their old devices stop
  working, and what's shared with them comes back as everyone's Keystead syncs. Under
  People › You, "Let the owner recover my own logins and folders" (escrow) brings back
  their own logins and the folders only they are in too, at the cost of the owner being
  able to open them. A device they still have warns them on every page and can cancel a
  recovery they didn't ask for, unless the owner chose to sign out their devices when
  starting it (then their Recovery Kit gets them back in). Needs a 0.13.0 server, and
  every app updated first.
- **Exporting:** File › Export Logins… saves every login you can open to a KeePass file
  (.kdbx), encrypted with a passphrase you choose, after Touch ID. Folders become groups
  and one-time codes come along; KeePassXC and KeePass open it, and Import reads it back.
  The file is encrypted before it's written, and only you can read it.
- **Recently Deleted:** a deleted login stays in Recently Deleted (in the sidebar) for 30
  days, for everyone who could edit it, with who deleted it and when. Bring Back returns it
  to everyone who had it; Delete Now… deletes it for good, and Delete All… everything
  there. Needs a 0.9.0 server; with an older one, it says so.
- **Quick search:** ⇧⌘Space (Settings › General: ⌥⌘K, ⌃⌥⌘K or off) opens a Spotlight-style
  box over any app. Type, pick with the arrows, and Return copies the password (Shift-Return
  the username, Option-Return the one-time code) and closes it, so the app you were in is
  still in front to paste into. It
  unlocks with Touch ID first if needed. It uses Carbon's hot key API, which needs no
  Accessibility permission and works in the App Sandbox.
- **Updates:** once a day (Settings › Updates, on by default) and from Keystead › Check for
  Updates…, the app asks GitHub for this repository's latest release, sending only its name
  and version as the user agent (`Keystead-macOS/0.13.1`). When a newer release has the Mac
  app attached, the window, the menu bar panel and Settings say so, with Download… opening
  the release's page; a closed notice stays closed until a newer version. Nothing is
  downloaded or installed by the app itself. The check lives in `keystead-client`
  (`updates.rs`); `cargo test -p keystead-client updates -- --ignored` asks GitHub for real.
- **Menu bar icon:** a quick panel to search and copy without opening the window. Clicking
  a login copies its password, and so does Return for the first match.
- **Dock icon:** shown by default. Settings > General can turn it off, leaving only the
  menu bar icon.
- **Approving people:** the owner's Keystead approves whoever joins with an invite line on
  its own, as the key on the line proves the keys they joined with are theirs; while
  invites are out it syncs every minute. Someone who joined with a line from an older
  Keystead, or whose keys don't match the invite (a warning says so), waits for the owner to
  type in the fingerprint they read out (in person or on a call). Keystead checks it
  against the keys they joined with, ignoring spaces, dashes and capitals.
- **Recovery Kit:** the account secret as 24 words, shown after Touch ID (hidden until
  asked for), printable, or copied as words alone to this Mac's clipboard for 30 seconds
  (People › You, or Settings › Account). The owner is asked to save one right after setup.
  Recovering on a new Mac checks the owner's fingerprint from the kit before registering
  anything (the owner can leave it out); the old Mac can then be removed from the device
  list under People › You. Needs a 0.2.0 server.
- **Adding a device:** Add a Device… (People › You, under Your devices) shows a line to
  paste into the new Mac's welcome screen (Add this Mac). The new Mac shows a code; typing
  it here and confirming with Touch ID sends the account across, sealed so only that Mac
  can open it, and it adds itself. Needs a 0.8.0 server; without another device, the
  Recovery Kit still works.
- **Auto-lock:** locks after 5 minutes without using Keystead, whatever else happens on the
  Mac (Settings › Security: 1 to 60 minutes, or never), and at once when the screen locks,
  the Mac or its display sleeps, or another user takes over the screen. Locking this way
  also clears the clipboard if it still holds a password Keystead copied. A Debug build
  launched with `-autoLockTest` prints the time since Keystead was last used every second
  and locks after 5 seconds.
- **Signing in again:** when the server needs this Mac to sign in with its key again (24
  hours after it last did, after the server forgot the session, as in a restart, or every
  15 minutes with a server before 0.14.0), Keystead locks instead of macOS asking for Touch
  ID or the password out of the blue, and says why on the lock screen. Unlocking signs in.
- **Sign out:** People › You, Settings › Account or Vault › Sign Out, after a confirmation
  and Touch ID or the Mac password, whether Keystead is locked or not. The
  server forgets this Mac, and the account's files and keys here are deleted; coming back
  takes the Recovery Kit.
- **Keys:** two Secure Enclave keys per Mac. One signs in to the server
  (`ecdsa-p256-sha256`), one unwraps the account secret. One Touch ID approval covers
  both.
- **Shared client:** the `keystead-client` library does sign-in, sync, sharing and
  signature checks. The account keys stay inside Rust and never reach Swift.
- **Copying passwords:** copied passwords stay on this Mac (no Universal Clipboard), are
  marked concealed for clipboard managers, and after 30 seconds, if still on the clipboard,
  give way to what was there before you copied (kept in memory only). Copying several in a
  row brings back what was there before the first, never an earlier password; another
  app's secret is cleared, not put back; locking because you're away, and quitting, just
  clear. On
  macOS 26 and later, reading the clipboard can make macOS ask, so Keystead only puts
  things back if it may paste from other apps without asking (System Settings › Privacy &
  Security); otherwise it just clears, as before.
- **Debug builds** are a separate app, "Keystead Dev" (`….Keystead.dev`), with their own
  data and an orange icon. Development never touches a real vault, and the two are easy
  to tell apart.

## Building

Requirements: Xcode 16 or later, and Rust with both Mac targets
(`rustup target add aarch64-apple-darwin x86_64-apple-darwin`).

Build the Rust core once after cloning. Xcode then rebuilds it as part of every build:

```sh
scripts/build-core.sh
open Keystead.xcodeproj
```

Or from the command line:

```sh
xcodebuild -project Keystead.xcodeproj -scheme Keystead -configuration Release \
    -derivedDataPath build/DerivedData build
```

The script writes `Frameworks/KeysteadCore.xcframework` (a universal static library with
its C header) and `Keystead/Generated/keystead_ffi.swift` (the Swift API). Both are
generated, so git ignores them.

## Looking at the UI without a server

Debug builds have a demo mode with made-up data, no server and no Touch ID. `-demo` shows
a team of three; `-demo alone` shows an owner who hasn't invited anyone yet. Add
`-snapshot` to step the window through its sections, save a picture of each plus how its
columns are laid out, and quit:

```sh
build/DerivedData/Build/Products/Debug/Keystead.app/Contents/MacOS/Keystead -demo -snapshot
open ~/Library/Containers/io.github.elquimista.Keystead.dev/Data/tmp/snapshots
```

With the team of three, that includes each sheet, the welcome and lock screens (`w…`),
each Settings tab (`s-settings-…`) and the menu bar panel (`p…`, opened from its menu bar
icon). The report also records, frame by frame, how the Settings window, the panel and
the sheets that load something change height, to check they glide rather than jump.
`-windowsOnly` runs just that part and Settings, and `-slowDemo` makes the demo's loads
as slow as a distant server's. Add `-NSRequiresAquaSystemAppearance YES` for light mode.
Without `-demo`, on a Mac where Keystead Dev isn't set up yet,
`-welcome join|setup|add|recover|recover-help` opens the welcome screen on that page.

To see how the window copes with a big team, `-demo big` has 5,000 logins, and `-measure`
prints how long the list's search and quick search take per keystroke and how much memory
the app uses, then quits. Build with optimization for numbers that mean something, in a
folder of its own:

```sh
xcodebuild -project Keystead.xcodeproj -scheme Keystead -configuration Debug \
  -derivedDataPath build/MeasureData build CODE_SIGN_IDENTITY=- SWIFT_OPTIMIZATION_LEVEL=-O
build/MeasureData/Build/Products/Debug/Keystead.app/Contents/MacOS/Keystead -demo big -measure
```

The Rust core's side, opening and listing a vault with that many logins, is
`cargo run --release -p keystead-client --example vault_bench -- 5000`.

`-checkConnection` connects to a few servers on the internet from inside the app's
sandbox, as the core does, prints whether macOS accepted each certificate (example.com
should be accepted, badssl.com's self-signed, expired and wrong-host ones refused), and
quits. It needs no server or Touch ID, and sends nothing about the Mac or its account.

Release builds take a little over a minute longer than Debug ones: the core is built with
link-time optimization (the `app` profile in `Cargo.toml`) and the app's symbols are
stripped, which together halve its size.

## Icons

`scripts/make-icons.swift` draws every icon into `Keystead/Assets.xcassets`: the app icon
(teal for Release, orange with a DEV bar for Debug) and the menu bar template images (the
Debug one carries a dot). The mark is a key ring: three keys on one ring, a team's keys
kept in one place. To change the design, edit the script and rerun it; it can also write a
side-by-side preview:

```sh
swift scripts/make-icons.swift /tmp/icon-preview.png
```

## Signing

Three levels, from no setup at all to a notarized download:

| Level | Who it's for | Setup |
| --- | --- | --- |
| Ad hoc ("Sign to Run Locally") | Anyone building on their own Mac, and CI's checks | None; this is the default |
| Apple Development | Day-to-day development with a stable signature, and the app attached to GitHub releases | A free Apple account is enough. Copy `Config/Signing.local.xcconfig.example` to `Config/Signing.local.xcconfig` and set your team ID. For releases, the certificate goes in repository secrets: see Publishing the Mac app in the main README |
| Developer ID + notarization | Distributing to other Macs | A paid Apple Developer Program membership ($99 a year) and a Developer ID Application certificate |

`Config/Signing.local.xcconfig` is git-ignored, so team details stay out of the repository.

**Without a paid membership,** builds can't be notarized. Anyone who downloads one gets a
warning that Apple couldn't check the app for malware. Since macOS 15, the only way past it
is System Settings > Privacy & Security > Open Anyway. That's acceptable for a few
technical testers, but not for rolling out to a team. Enrolling as an organization shows
the company as the developer and needs a D-U-N-S number.

### Choices made with distribution in mind

- **Hardened Runtime is on** for every build; notarization requires it.
- **App Sandbox is on**, with one extra permission: outgoing network connections. That
  limits what a compromised app could reach and keeps the Mac App Store possible.
- **Release builds never carry the debugging entitlement** (`get-task-allow`), which
  notarization rejects. Xcode adds it to development builds unless told not to.
- **The Rust core is a static library**, so the app contains no separate binaries that
  would each need signing and notarizing.
- **No Keychain entitlement yet.** The device key handle and the wrapped account secret
  live in the app's sandbox container. Neither is secret on its own: the handle works only
  in this Mac's Secure Enclave after Touch ID or the Mac password. Keychain access groups
  would need a provisioning profile, so they're left out until they're needed.
- **Bundle identifier:** `io.github.elquimista.Keystead`, set in `Config/Signing.xcconfig`.
  Choose the permanent one before the first public release; it ties together the app's
  sandbox container, notarization and updates.

### Releasing (needs a Developer ID certificate; not yet tried)

Pushing a version tag already attaches a build signed with the owner's Apple Development
certificate to the tag's GitHub release (see Publishing the Mac app in the main README).
Notarizing it takes the steps below, which the macOS workflow could then run with the
Developer ID certificate and notarization credentials as repository secrets. By hand:

1. In `Config/Signing.local.xcconfig`, uncomment
   `CODE_SIGN_IDENTITY[config=Release] = Developer ID Application`.
2. Store notarization credentials once:
   `xcrun notarytool store-credentials keystead-notary --apple-id <email> --team-id <team>`
3. Archive, export, notarize and staple:

```sh
xcodebuild -project Keystead.xcodeproj -scheme Keystead -configuration Release \
    -archivePath build/Keystead.xcarchive archive
xcodebuild -exportArchive -archivePath build/Keystead.xcarchive \
    -exportOptionsPlist Config/ExportOptions.plist -exportPath build/export
ditto -c -k --keepParent build/export/Keystead.app build/Keystead.zip
xcrun notarytool submit build/Keystead.zip --keychain-profile keystead-notary --wait
xcrun stapler staple build/export/Keystead.app
```
